- The current native candidate adds a user-confirmed JSON export through the device share sheet and authenticated private-document opening through a device viewer. Exported/shared copies outside DoctorAI are not removed by DoctorAI deletion. Session credentials are excluded from the export. App-owned temporary exports, downloads, camera images and picker copies are cleaned up; source/synthetic checks do not prove cleanup on every Android device or in an external viewer. Reconcile these user-initiated transfers and new Expo Sharing/Intent Launcher modules with the final SDK inventory and Play definitions.
- The exact 1.0.8 (12) signed AAB has been inspected: min SDK 24 / target SDK 36, embedded runtime 1.0.8, production channel and valid CMS signature/all 791 signed-entry digests. Final uses-permissions: CAMERA, INTERNET, WRITE_EXTERNAL_STORAGE, ACCESS_NETWORK_STATE, USE_BIOMETRIC, USE_FINGERPRINT and the app's signature-protected dynamic-receiver permission. Broad photo read, microphone, overlay and vibration permissions are absent. SecureStore is excluded in packaged legacy/cloud/device-transfer backup XML. Permission presence is not proof of collection: the current SecureStore options do not enable biometric authentication. Audit infrastructure and SDK behavior before declaring data categories absent.
- Local state writes now use byte-limited SecureStore chunks, a commit pointer and recovery journal. Failed writes preserve the committed snapshot. Startup blocks edits until hydration; account outages retain device entries, while confirmed 401/403 expiry removes active sign-in. Deletion invalidates late callbacks, waits for pending upload/sync work and lists cloud documents afresh; cloud failure keeps device data for retry. These source behaviors need installed-device checks.

- DoctorAI is a health app: users can record health details, manage medicines and appointments, save medical documents, search medical research, ask an AI health-education assistant and scan a medicine label. Play's Health Apps declaration is required even for testing tracks. Likely feature areas include healthcare services/management, medication/treatment management and medical reference/education; confirm the actual choices from the final intended purpose and current Play Console form.
- The app stores state locally in Expo SecureStore. After a user signs in, it syncs selected health records to DoctorAI. The app does not sync its conversation history to the DoctorAI account API, but chat messages are sent to OpenAI when the user taps Send.
- Android label scanning had a release-blocking consent mismatch: the API required `consent: true`, but the app omitted it. The app now presents a disclosure with an affirmative “Agree & open camera” action before requesting camera access and sends the consent flag with the image.
- The chat route relied on the OpenAI Responses API default storage behavior. It now sets `store: false`, matching the label-scan route. This prevents Responses API application-state storage; it does not remove OpenAI's default abuse-monitoring log retention, which may last up to 30 days. A shorter-retention exception for this API project is unconfirmed.
- The local site candidate now contains a standalone `/account-deletion` request page, linked from Privacy and included in the sitemap and PWA cache. The static verifier passes at 82 required files and 12 public pages. Android Settings now links to this page and retains the prefilled deletion-request email; both routes still need a physical-device test and staffed support. The candidate is not yet a working public resource until deployed.
- Production was checked read-only on 4 October: `https://www.doctoraiworld.com/privacy` returned 200 and lists Europe PMC as a provider, but does not explain that research search topics are forwarded there; `/account-deletion` returns 404. The Privacy Notice has since gained a deletion section and explicit forwarding disclosure locally. Deploy and verify the reviewed production pages and resource URL before submission.
- Android prebuild source now has merge-removal directives for `READ_EXTERNAL_STORAGE`, `RECORD_AUDIO`, `SYSTEM_ALERT_WINDOW` and `VIBRATE`; its main manifest also includes `CAMERA`, `INTERNET` and legacy `WRITE_EXTERNAL_STORAGE`. The app uses `launchCameraAsync` for a user-consented label photo, and its document selection uses Android `ACTION_OPEN_DOCUMENT`. Expo's camera implementation requests legacy write permission below API 29, so it remains for older Android devices. No broad photo-library API is called. This is generated-source evidence, not the final merged manifest; inspect the signed AAB and SDK permissions before completing the Play form.

## Data map to reconcile with the Play Data safety form

Google defines collection as transmitting user data off-device, including by SDKs. It requires app and SDK practices to be represented. A transfer to a service provider can qualify for a sharing exception only when that provider processes data on the developer's behalf and on the developer's instructions. Treat the rows below as a conservative draft, then confirm exact definitions and exclusions in the live form.

Sign-in is optional for basic local organization. | Sent to DoctorAI and Google sign-in services. Confirm how Google profile image and account subject are used and whether each transfer qualifies for a service-provider exception. |

## Likely form answers to verify

- **Data collection:** Yes. Health/account data and user-selected documents are transmitted to DoctorAI; chat, research queries and consented scan images are transmitted for requested functionality.
- **Encrypted in transit:** Likely yes for the listed app/backend/provider calls, which use HTTPS. This answer requires a final endpoint and SDK audit: Play permits the encryption claim only if it applies to all collected/transmitted user data, including all SDKs.
- **Deletion mechanism:** Do not claim this until tested end to end. The current source has a local health-data deletion control and an in-app account-deletion action that opens a prefilled email request to support; the user must review and send it. A standalone external resource now exists in the local site candidate, while Production still returns 404 at that route. Confirm the reviewed production URL works, support acknowledges and completes requests, account identity and documents are removed, provider deletion requests are made where supported, subscription renewal is handled, and any retained records are disclosed. Health-data deletion is not account deletion.
- **Collection optionality:** Most personal records, research searches, chat and label scans are user-provided/initiated. Sign-in is optional for basic local organization but required for chat, scanning and cloud sync. Confirm optional/required per form data type and the actual released UI.
- **Purpose choices:** App functionality and account management are supported by the source. Do not choose advertising, analytics, or personalization without evidence for those purposes. Determine whether any content used in an AI response meets Play's personalization definition.
- **Sharing:** Do not answer from vendor names alone. Google excludes some transfers where a service provider processes data only on the developer's behalf and instructions, and some user-initiated transfers. Confirm contract and flow treatment for OpenAI, Google sign-in, Vercel and Europe PMC. Document the decision for each data type.
- **Health Apps declaration:** Select all categories/features that match the final app's intended purpose and actual features; no final medical-device status or category is asserted by this worksheet. Obtain qualified intended-purpose/regulatory review before completing the declaration or adding a non-device disclaimer to the store listing.
