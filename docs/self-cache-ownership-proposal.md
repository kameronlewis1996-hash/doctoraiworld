# Self-profile cache ownership and explicit recovery

Implemented after the owner approved the scoped cache fix. No production promotion or legal-page publication is included.

## Boundary

Health state starts blank until `/api/auth/google` confirms the session-derived opaque `user.accountId`. Email, names, timestamps, URL parameters and parsed cookies never establish ownership. New optional self caches use an atomic version-2 envelope keyed and validated against that account ID and `profileId: self`. Managed profiles still use no persistent health cache. Browser storage remains plaintext; this prevents accidental account mixing, not access by someone with device or DevTools access.

All eleven existing unscoped health keys remain byte-for-byte in quarantine. Startup, chat, scan and cloud sync never read them as current health records. No old key is deleted, rewritten, auto-assigned or auto-uploaded. Device preferences remain separate. Anonymous new health data stays in memory for the session, with explicit health export available; signing in preserves a nonempty guest session only as a separate in-memory recovery source, never as the account record.

Sign-out/account replacement stops queued sync, clears forms/scans/chat/current display, advances request/person epochs, and preserves the prior account cache. Late auth GET/POST and cloud JSON callbacks recheck their account/request before committing. Re-authentication can load only that owner's envelope with device-storage consent. The server record is fetched before saves are allowed. Unsynced owner-bound copies are preserved separately for manual review/export; startup never chooses a cache by a newer timestamp or uploads it automatically. Preservation always attempts an account-bound in-memory copy first. Durable preservation requires both the explicit device-storage choice `yes` and its enabled flag. Session-only or undecided users make no persistent health writes. Quota, blocked storage or a corrupt prior backup retains the newest edits in memory for review/export and blocks overwriting the canonical device cache; the notice explicitly says the device backup is unavailable, never that durable preservation succeeded. If neither memory nor durable preservation succeeds, the current edits, candidate and original revision remain unchanged and automatic writes stay paused. Malformed prior backup bytes are retained.

## Recovery

Privacy offers local export and explicit review for legacy, guest, preserved owner copies and prior recovery drafts. Legacy entries are labelled unlinked; their contents do not appear in the ordinary health display. A signed-in user must select Myself, wait for their account record, review all fields under the named account, and affirm the records are their own. Cancel/Back does not apply anything. Invalid copies remain exportable and cannot be opened as records.

A confirmed review creates a separate paused draft. It does not merge people, replace the canonical cache, upload automatically, or enable AI/label scans. The original account snapshot remains in the recovery envelope. Manual edits stay in the draft. Returning to saved account records restores the server view while retaining the draft; reloading requires another explicit review to continue. Replacing an earlier recovery preserves the newest live draft as an account-bound memory copy first; a durable copy is attempted only with explicit device-storage consent. Session-only manual draft edits update the in-memory export source. Memory-only and failed-device-backup notices tell users to export before closing. Export contains exact legacy strings where present and the prior account snapshot; document files are not included.

Only **Save reviewed recovery to this account**, with a separate named-account confirmation, writes the draft to self storage using the current server compare-and-set revision. A changed revision fails safely and keeps the draft for export/review. Completed recovery and its prior snapshot remain exportable. Free accounts can export and recover their own self records. Subscription, managed namespaces and server record schemas are unchanged.

## Explicit self-data deletion

After the existing account/document deletion completes and the user has explicitly confirmed the scope, self deletion removes exactly the current verified owner's three versioned browser keys (`record`, `preserved`, `recovery`). This applies even if the user has since switched device storage off: the separate deletion confirmation names those prior caches/backups. It also clears that owner's in-memory self snapshot, preserved copies, recovery drafts, pending candidate/review and active prior-state references. Another owner, managed profile, unlinked legacy bytes and unknown guest-session source stay untouched. No bulk storage enumeration or automatic purge is used. There is no live legacy-cleanup button; a separately reviewed, explicit legacy-cleanup design may be considered later.

Completed deletion no longer exposes the removed owner backups through recovery/export or rehydrates them on reload. Request/person epochs invalidate pre-deletion callbacks. Cancel or server-deletion failure retains local copies. If browser removal is blocked or cannot be verified, the UI reports **device cleanup incomplete**, pauses sync and asks for a retry; it cannot promise deletion of inaccessible bytes. The new tests perform only synthetic future-behavior deletion, never real user data removal.

`node scripts/verify-self-cache-consent.cjs` verifies session-only/undecided delayed-GET edits, dirty in-memory account-session restoration, recovery replacement/latest draft export, zero persistent health writes without explicit consent, quota/blocked/corrupt backups with honest notices, account-bound memory fallback and total-preservation failure retaining live edits/revision. It fails on the earlier `8738874` hub at the no-consent write assertion.

`node scripts/verify-self-cache-deletion.cjs` verifies fixed current-owner cleanup, no leftover recovery export/reload/late-GET resurrection, other-owner and unlinked byte preservation, Cancel, stale owner, remote failure, local-removal failure and managed-person deletion isolation. `DOCTORAI_BROWSER_BIN=<installed agent-browser> PROFILE_PREVIEW_PORT=4183 node scripts/verify-self-cache-consent-browser.cjs` adds 15 actual localhost browser checks for opt-out preservation/replacement/export and scoped future self deletion. They use synthetic sessions/health/storage only, with zero paid API or external storage calls.
