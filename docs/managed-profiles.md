# Pro family & loved ones profiles

One signed-in account manages private profiles with a required display name and optional relationship. There are no invitations, separate logins or cross-account sharing.

`/api/health/profiles` lists, creates and edits profiles. Creation uses a UUID idempotency key and Redis HSETNX; concurrent retries create one profile. Session revocation and durable Pro entitlement checks run on the server. Owner namespaces and stored owner validation prevent another account from resolving a profile ID. Client account context also rejects stale-tab requests after cookies change accounts.

Self records retain the original `health-state` field and document namespace. Managed profiles use separate encrypted `managed-health:<profileId>` fields, document metadata namespaces and private encrypted Blob paths. Medications, allergy/safety terms, notes, appointments, providers, timeline/symptoms, measurements, tasks and approved memory are all scoped together. Managed data is transient in memory and uses authenticated encrypted server persistence; it is never written to the owner's localStorage or sessionStorage. Legacy self cache behavior is preserved; unknown legacy cache ownership across a full reload remains an existing limitation.

The Profile page has a Family & loved ones section; an active-person selector appears across the hub. Switching loads the selected namespace, closes forms, clears scan/file inputs, medication results, chat and draft briefs, and waits for any originating save/upload/scan/chat/safety operation (including JSON body parsing) to finish. While the target GET is pending, controls and event handlers reject new work. Parsed results recheck the captured person and account before changing state. An unfinished form can be cancelled or discarded. Failed saves keep changes unless discard is explicitly confirmed.

Archiving keeps records. Archived and downgraded managed profiles are read only, with view/export/download/delete available. Pro is required to create, edit, restore, upload or update managed records. Reading and deletion never require an active subscription. Document DELETE also removes only that document's references from encrypted health state on the server, so deleted entries do not reappear on reload; it does not grant general Pro write access. Billing and prices are unchanged.

Pro managed profiles support the existing chat, AI briefings and OCR/camera label scans with the same consent, provider and clinical rules. The server validates the selected owner/profile and rejects archived/Free managed actions. Managed chat ignores request-body memory and reads only that person's approved Health Memory from their encrypted server record. Pending changes must sync before a managed chat/briefing. OCR receives the selected image only, never another person's medication/allergy context, and returns its profile ID; extracted fields still require user review. Conversations and scan forms clear on switching. All verification uses synthetic provider output, with no real OCR or paid API calls.

External NZF/DrugBank catalogue/safety workflows and sharing remain unavailable for managed profiles. Their existing signed-use/licensing, NZ-scope, provider and consent gates are unchanged. These workflows require separate scope/consent/provider integration verification before enabling managed use; this is a remaining limitation. Manual records, local medication guidance, visit briefs and document storage are supported.

## Verification

Run `pnpm run verify:profiles` for synthetic server tests. They use real signing, session validation, encryption and route handlers against an in-memory Redis/Blob transport; every attempted external request is rejected. Coverage includes self/two-person records, other-owner/unknown/crafted IDs, forged fields, atomic repeated clicks, private documents, archive/restore, Free/expired/revoked entitlement, stale cookies, changed-account tabs and deletion isolation. No paid calls or production storage are used.

Run `pnpm run preview:profiles`, then open `http://127.0.0.1:4173/health-hub#profile` for the local synthetic preview. This helper binds to localhost and must not be deployed. Synthetic controls under `/__test/` allow plan/account/latency/failure changes for browser verification. `scripts/` is excluded from Vercel deployment.

Run `node scripts/verify-person-switch.cjs`, `node scripts/verify-preview-isolation.cjs`, and `node scripts/verify-managed-ai.cjs` for delayed GET/JSON regressions, runtime fail-closed Preview checks, and synthetic chat/OCR scope checks. The switch regression fails on the earlier `8900354` hub source and passes after the transition lock. The local preview mocks both storage and AI transport; neither can contact live services.

Browser verification with Chromium/agent-browser covered profile creation, Cancel, edit, archive/restore, Cedar/River allergy-note isolation, no managed browser cache, pending save, failed save Cancel/discard, unfinished form Cancel/discard, transition-time file/form blocking, managed chat/OCR and clearing their state, and 320/390/768px layout. These are local tests with synthetic storage/providers, not authenticated tests against deployed infrastructure.

Reference-image materialization failed after one allowed retry, so the implementation follows the existing repository Profile style. No reference image or real identity is committed. PROJECT_RULES.md and local .agents guidance were absent in the saved environment and latest main.

Existing full-project checks have baseline failures: the public MCP file has an unescaped apostrophe; static verification rejects existing printable-resource form fields and appointment-checklist links, and finds an existing missing index-page CSP hash. The managed-profile, server, medication scan/safety/database/local UI, NZF and Stripe-pricing focused checks pass. Keep these baseline failures separate from feature verification.

Vercel Preview private access now requires dedicated `PREVIEW_AUTH_SECRET`, `PREVIEW_KV_REST_API_URL` and `PREVIEW_KV_REST_API_TOKEN`. It never falls back to the generic keys. Equal inherited keys or a KV endpoint on the same origin are rejected; absence fails closed before any session/store access. Documents also require a distinct `PREVIEW_BLOB_READ_WRITE_TOKEN`, passed explicitly to every Blob SDK call. Configure these only for an existing physically separate test database/private Blob store and separate test signing secret. This guard cannot establish whether two externally supplied different credentials/endpoints secretly alias one physical store; deployment owners must verify that allocation. No configuration or credentials were created or changed in this task.

Authenticated deployed QA remains blocked until existing isolated Preview configuration is verified, with a synthetic account and durable test Pro entitlement. Do not use shared production storage, real health data, or real OCR. Static preview rendering and successful builds do not prove authenticated functionality.
